# Интеграция с аккаунтом SoundCloud

Документ описывает предполагаемую интеграцию BetterSoundCloud с официальным SoundCloud API: как пользователь подключает аккаунт, как приложение получает доступ, какие функции поддерживаются и какие правила нужно учитывать.

> **Состояние проекта:** OAuth-поток и интеграция с API SoundCloud пока не реализованы. Сейчас работает промежуточный вариант — подключение аккаунта вставкой access token: Go sidecar проверяет токен через `GET /me`, хранит его локально с правами `0600` и отдаёт renderer-у только признак входа и профиль. Описанная ниже схема — целевая архитектура для полноценного входа.

## 1. Что означает «войти через SoundCloud»

Пользователь входит в свой существующий аккаунт SoundCloud и подтверждает доступ BetterSoundCloud. Отдельный аккаунт BetterSoundCloud и пароль SoundCloud приложению не нужны. SoundCloud возвращает приложению OAuth-токен, связанный с конкретным пользователем. По нему приложение может читать доступные этому пользователю данные и выполнять разрешённые действия от его имени.

Приложение не должно показывать собственную форму ввода пароля SoundCloud, собирать пароль или пытаться войти через него. Авторизация проходит на официальной стороне SoundCloud.

## 2. Что требуется до разработки

Для работы с API нужны учётные данные приложения SoundCloud: `client_id` и `client_secret`. Их получает разработчик при регистрации API-приложения SoundCloud. Согласно текущей [инструкции по регистрации](https://developers.soundcloud.com/docs/api/register-app), для регистрации приложения требуется подписка SoundCloud Artist Pro.

`client_secret` нельзя добавлять в исходный код, renderer, desktop bundle или публичный репозиторий. Документация SoundCloud требует секрет для обмена authorization code и обновления токена; поэтому целевая схема включает небольшой сервер авторизации, который хранит секрет в защищённой конфигурации.

Пользователям приложения не нужно создавать API-приложение или иметь Artist Pro: они лишь авторизуют свои SoundCloud-аккаунты в приложении разработчика.

Подписка Artist Pro даёт возможность зарегистрировать API-приложение, но сама по себе не является разрешением на любой продукт. Текущие [условия API](https://developers.soundcloud.com/docs/api/terms-of-use) отдельно запрещают использовать API для альтернативного цифрового музыкального сервиса, который агрегирует и транслирует контент разных пользователей по запросу, если это явно не лицензировано; также ограничено копирование существенной части функций/общего опыта SoundCloud. Это напрямую затрагивает идею BetterSoundCloud как альтернативного клиента. До разработки полной интеграции нужно получить от SoundCloud явное подтверждение/лицензию, что такой сценарий разрешён.

## 3. Вход пользователя: OAuth 2.1 с PKCE

SoundCloud использует Authorization Code flow с обязательным PKCE. Поток состоит из следующих шагов:

1. Пользователь нажимает **«Войти через SoundCloud»**.
2. Tauri/Rust backend генерирует криптографически случайные `state` и `code_verifier`. Из `code_verifier` вычисляется PKCE `code_challenge` методом `S256`.
3. Приложение открывает официальный адрес авторизации SoundCloud в браузере/официальном OAuth webview, передавая `client_id`, зарегистрированный `redirect_uri`, `response_type=code`, `code_challenge`, `code_challenge_method=S256` и `state`.
4. Пользователь входит на SoundCloud и подтверждает запрос.
5. SoundCloud возвращает authorization code на зарегистрированный callback приложения. Для desktop-приложения документация описывает custom protocol redirect, например `bettersoundcloud://oauth/callback`; фактическую схему и URI нужно зарегистрировать для приложения.
6. Tauri/Rust backend сверяет полученный `state` с исходным. При несовпадении поток прекращается.
7. Tauri/Rust backend передаёт authorization code и `code_verifier` серверу авторизации. Сервер обменивает их на `https://secure.soundcloud.com/oauth/token`, добавляя `client_id`, `client_secret`, точный `redirect_uri` и `grant_type=authorization_code`.
8. Сервер возвращает токены приложению. Tauri/Rust backend получает профиль через `GET https://api.soundcloud.com/me` и показывает подтверждённое имя/аватар пользователя.

`redirect_uri` при обмене кода должен в точности совпадать с URI из запроса авторизации. `state` защищает от подмены callback, а PKCE связывает обмен кода с начатой на этом устройстве авторизацией.

Не следует изобретать OAuth `scope` значения: в актуальных примерах SoundCloud доступы определяются пользовательским согласием и типом OAuth-потока. Проверять доступные поля и операции нужно по текущему [API Guide](https://developers.soundcloud.com/docs) и [API Explorer](https://developers.soundcloud.com/docs/api/explorer/).

## 4. Хранение и обновление токенов

Ответ token endpoint включает `access_token`, `refresh_token`, `expires_in` и `scope`. Access token действует примерно час. Refresh token одноразовый: после каждого успешного обновления его нужно немедленно заменить новым значением из ответа.

Рекомендуемое разделение ответственности:

- Сервер авторизации хранит `client_secret` и выполняет обмен authorization code и refresh token.
- Tauri/Rust backend хранит пользовательские токены только локально в системном credential store, а не в renderer, `localStorage`, логах или настройках в открытом виде.
- Renderer не получает прямого доступа к Node.js и секретам. Вызовы Rust-команд проходят через ограниченный Tauri invoke API.
- Не сохранять форму или содержимое токена и не полагаться на его внутренний формат: SoundCloud предупреждал о переходе к JWT-формату.

При запросах к API используется заголовок `Authorization: OAuth ACCESS_TOKEN`. Если API вернул `401` из-за истёкшего токена, приложение запрашивает у сервера авторизации обновление, сохраняет обе новые пары токенов и повторяет исходный запрос один раз. Ошибку обновления нужно показать пользователю и предложить подключить аккаунт повторно.

Client Credentials flow годится для некоторых публичных ресурсов, но не даёт доступ к личным лайкам, плейлистам и действиям от имени пользователя. Он не заменяет вход через SoundCloud.

## 5. Выход и отзыв доступа

При выходе приложение отправляет текущий access token на `POST https://secure.soundcloud.com/sign-out`, затем удаляет локально сохранённые токены и пользовательские данные/кэш. Если пользователь отозвал доступ или токен стал недействителен, приложение должно перестать использовать связанные с аккаунтом данные и предложить повторный вход.

## 6. Какие функции API можно связать с интерфейсом

Точные параметры, типы идентификаторов и ответы следует брать из [актуальной OpenAPI-спецификации/API Explorer](https://developers.soundcloud.com/docs/api/explorer/). Основные группы:

| Возможность в приложении | Примеры API |
| --- | --- |
| Профиль подключённого пользователя | `GET /me` |
| Лайкнутые треки и плейлисты | `GET /me/likes/tracks`, `GET /me/likes/playlists` |
| Лайк/снятие лайка | `POST` и `DELETE /likes/tracks/{track_urn}`; соответствующие endpoints для playlists |
| Плейлисты пользователя | `GET /me/playlists`, `GET /playlists/{playlist_urn}` |
| Поиск | `GET /tracks`, `GET /playlists`, `GET /users` с параметрами поиска |
| Недавно прослушанное | `GET /me/recently-played/tracks` |
| Подписки и лента | `/me/followings`, `/me/feed` и связанные endpoints |
| Комментарии | `GET` и `POST /tracks/{track_urn}/comments`, если комментарии разрешены автором |
| Воспроизведение | Данные трека и stream endpoints — только когда API разрешает поток для этого трека |

Для списков API поддерживает пагинацию; нужно продолжать запросы по `next_href`, а не предполагать, что первая страница содержит все лайки или плейлисты. Персональные карточки главной стоит строить из реально полученных данных пользователя, а при пустом или недоступном ответе показывать понятное пустое состояние.

## 7. Воспроизведение и работа с контентом

Не каждый трек можно воспроизводить вне SoundCloud. Доступ может быть ограничен автором, регионом или условиями доступа; API может вернуть `preview` или `blocked` вместо полного потока. Приложение должно уважать эти статусы и не обходить ограничения.

При показе или воспроизведении контента нужно:

- указывать автора и SoundCloud как источник;
- давать ссылку на оригинальный трек SoundCloud;
- использовать только доступный SoundCloud способ воспроизведения и актуальные правила атрибуции;
- не удалять и не скрывать атрибуцию, рекламу или ограничения доступа.

Условия SoundCloud запрещают функции постоянной загрузки, офлайн-доступа и долговременного хранения аудио. Допускается лишь ограниченный session-based cache, необходимый для работы приложения в текущем сеансе; он не должен оставаться доступным после завершения сеанса. Поэтому раздел **«Загрузки»** нельзя превращать в скачивание или офлайн-хранилище SoundCloud-контента.

## 8. Пагинация, ошибки и обновление данных

- Для коллекций использовать `linked_partitioning=true` и следовать `next_href`.
- Обрабатывать `401` (невалидный/истёкший токен), `403` (нет доступа), `404` (ресурс недоступен) и `429` (ограничение частоты запросов); показывать пользователю понятное сообщение.
- Не обновлять токен параллельно несколькими запросами: refresh token одноразовый. Обновление следует сериализовать, чтобы два одновременных вызова не пытались погасить один токен.
- Учитывать, что лайк, плейлист или трек могут быть удалены, стать приватными или перестать быть доступными. Данные интерфейса должны следовать актуальным ответам API.
- Не собирать больше персональных данных, чем нужно функциям приложения. При отключении аккаунта удалить данные, относящиеся к этому пользователю, в соответствии с условиями SoundCloud и применимым законодательством.

## 9. Порядок практической реализации

1. Уточнить у SoundCloud допустимость продукта и получить API credentials для зарегистрированного приложения.
2. Поднять сервер авторизации с HTTPS, конфигурацией `client_secret`, обменом authorization code и refresh token.
3. Зарегистрировать desktop callback URI и подключить его обработку через Tauri deep-link integration для поддерживаемых ОС.
4. Добавить узкий Tauri command API, экран входа/выхода и системное защищённое хранение токенов.
5. Реализовать клиент API и сначала подключить `/me`, лайки, плейлисты и поиск.
6. Добавить воспроизведение только для доступных треков и выполнить требования атрибуции.
7. Проверить пограничные случаи: отказ пользователя, неверный `state`, истёкший access token, уже использованный refresh token, выход и отзыв доступа.
