# План: лирика для большинства треков

Документ описывает, что довести покрытие лирики до большинства библиотеки. Кода реализации
здесь намеренно нет — только диагноз, измерения и последовательность шагов.

## Как измерять

Эталонный инструмент — `scripts/lyrics-coverage.mjs`. Он прогоняет библиотеку через набор
стратегий и печатает, сколько треков нашла каждая. Это и есть «ориентир»: сначала получить
цифры, потом менять код, потом снова получить цифры.

```bash
node scripts/lyrics-coverage.mjs                              # scripts/lyrics-sample.txt, 41 трек
node scripts/lyrics-coverage.mjs моя-библиотека.txt --json отчёт.json
node scripts/lyrics-coverage.mjs --delay 200 --concurrency 3
```

Эталонный датасет лежит в `scripts/lyrics-sample.txt` — это выгрузка реальной библиотеки:
русский phonk, slowed/reverb версии, интернет-рэп и unreleased треки. Именно этот профиль
объясняет все проблемы ниже; на поп-хитах с английским текстом всё работает и без изменений.

Стратегии в скрипте идут в порядке нарастания и соответствуют шагам плана:

| Ключ | Стратегия | Шаг плана |
|---|---|---|
| `A_current` | `/api/get` exact, только synced — ровно как сейчас | базовая линия |
| `B_plain` | + принимать `plainLyrics` | шаг 2 |
| `C_search` | `/api/search` вместо exact | шаг 3 |
| `D_search_plain` | + `plainLyrics` | шаги 2–3 вместе |
| `E_normalized` | + нормализация названия | шаг 1 |
| `F_synthetic` | + тайминги из plain | шаг 5 |

- **Потолок синхронизации — 23 из 41 (56%), и он упирается не в стратегию, а в базу.**

  `You Could Be The One` (16 строк), `poison tearz` (26), `Stay Strange` (16). Синтетика

## Диагноз

Проверено чтением кода и живыми запросами к провайдерам.

1. **`plainLyrics` выбрасывается.** `lrclibLyricsResponse` (`main.go:1386`) объявляет только
   поле `SyncedLyrics`. LRCLib в ответе отдаёт и `plainLyrics`, и `syncedLyrics`. Если у записи
   нет таймингов, `parseLRC` возвращает пусто, `fetchSyncedLyrics` возвращает `false` — и
   найденный текст молча теряется, запрос уходит в Genius. Часть LRCLib отдаётся только как
   plain, поэтому целый класс треков не работает при наличии записи в базе.

2. **Используется только `/api/get`, который требует точного совпадения.** `/api/search` не
   вызывается никогда. Проверено на «ДИНАСТИЯ»: исполнитель в SoundCloud — `madk1d`,
   `/api/get?artist_name=madk1d` отдаёт `404 TrackNotFound`; та же запись в базе лежит под
   `VILLIAN, madk1d` и отдаёт 45 строк с таймингами. Разница только в имени исполнителя, а
   трек уже есть в базе.

3. **`/api/get` требует `artist_name`.** Без него `400 missing field artist_name`. То есть
   стратегия «поиск только по названию» на этом эндпоинте невозможна, а название трека в
   SoundCloud часто единственный надёжный идентификатор.

4. **В запрос уходит мусор из названия.** Запрос строится как `Artist + " " + Title`
   (`main.go:1252`) без очистки. Для `PIXELATED KISSES - JOJI [ SLIGHTLY 0.5x SLOWED + BASS
   BOOSTED].` в базу уходит bracketed-мусор, хотя исходный трек — `PIXELATED KISSES` от `JOJI`.

5. **Genius берёт первый результат без проверки.** `result.Response.Hits[0].Result.URL`
   (`main.go:1273`) — без сверки исполнителя, названия и длительности. Это хуже, чем пусто:
   пользователь получает чужой текст и не отличит его от своего.

6. **Genius парсится по HTML.** Класс `Lyrics__Container` (`main.go:1299`) — внутренняя деталь
   разметки Genius, которая меняется без предупреждения. Надёжность ниже, чем у LRCLib.

7. **Нет кэша.** Каждое открытие сайдбара (`LyricsSidebar` → `appGateway.trackLyrics`) делает
   сетевой запрос заново. Это и медленно, и съедает лимиты, и заставляет Genius отдавать 429.

8. **LRCLib периодически отдаёт `503 ServerOverloaded`, и лимит общий по IP.** В замерах
   доля 503 доходила до 30%+ после серии запросов. Без повторов это выглядит как «лирики нет»

## Находка замера: загрузитель ≠ исполнитель

Значимая часть библиотеки — это не оригиналы, а сторонние загрузки: sped-up, ремиксы и
фан-аккаунты. Исполнитель в SoundCloud для них указывает на загрузителя, а не на автора
трека. Проверено поиском по одному только названию:

| Трек в SoundCloud | Загрузил | Что в базе | Верно? |
|---|---|---|---|
| `I H3ART YOU` | `lovesage#1fan` | `BOY FANTASY — I H3ART YOU` (sync) | да |
| `Mr. Rager sped up` | `brx4y` | `Kid Cudi — Mr. Rager` (sync) | да |
| `I Want Things to Be Beautiful` | `Girls Rituals` | `Devi McCallion` — то же название (sync) | да |
| `antidepressant (winver Remix)` | `winver` | `Lloyd Cole — Antidepressant` (sync) | вероятно |
| `Just Staring` | `VYZEE` | `John Lennon — (Just Like) Staring Over` | нет |
| `What can i do (slowed)` | `Taida` | `A‐Trak — What Can I Do` | нет |
| `Secret Society` | `IN GOD WE TRUST` | `Europe — Secret Society` | нет |
| `NEON JUMP` | `Phonk Killer` | `Demi Lovato — Neon Lights` | нет |

Отсюда два вывода, которые и определяют дизайн:

- Поиск по одному названию возвращает правильный оригинал там, где поиск по паре
  «название + исполнитель» промахивается. Значит несовпадение исполнителя **нельзя**
  трактовать как провал — у SoundCloud-исполнителя просто другое значение смысла, чем у
  поля artist в базе.
- При этом тот же поиск подсовывает откровенный мусор. Значит расширять поиск без скоринга
  нельзя — это не улучшение, а замена «нет лирики» на «чужая лирика».

**Политика приёма кандидата:** название должно совпадать строго, длительность — близко,
исполнитель — не влияет на вердикт. Всё остальное отвергать. Это ровно тот случай, где
`durationMs` из `trackLyricsParams` решает, а не мешает.

### Ограничение этого вывода

Вывод проверен на всех 18 непокрытых треках, а не на восьми удачных. Поиск по одному
названию выдаёт примерно столько же мусора, сколько попаданий:

| Название | Что вернёт база | Вердикт |
|---|---|---|
| `face VLONE` | `FACE — Vlone` (sync) | **да** |
| `It Can't Come Quickly Enough` | `Scissor Sisters` (sync) | **да** |
| `antidepressant` | `Lloyd Cole` (sync) | вероятно |
| `Just Staring` | `John Lennon` (sync) | нет |
| `What can i do` | `A‐Trak` | нет |
| `Secret Society` | `Europe` (872 с) / `Title Fight` | нет |
| `FOREVER YOUNG` | `Young 501` | нет |
| `NEON JUMP` | `NONAH` / `Demi Lovato` | нет |
| `SAKEI` | `IVEL — Kaip Tu Sakei` | нет |
| `Люби Меня` | `Люби меня люби` | нет |
| `Улетаю в Париж`, `provoker-bugs and humans` | пусто | нет |

Итого честный прирост от поиска по одному названию — **около двух треков**, при шести
гарантированных промахах. Значит это не основной путь, а последний рубеж, и только с
обязательной проверкой длительности.

Отдельно найденный изъян скоринга: `tokenOverlap` в бенчмарке даёт `1.0` кандидату, чьё
название является **надмножеством** искомого — `Люби Меня` находит в `Люби меня люби`, потому
что обратное пересечение тоже полное. Таких кандидатов надо отсекать по асимметрии длин, иначе
скоринг из шага 4 будет пропускать чужое. Это общий принцип: подмножество — совпадение,
надмножество — повод насторожиться.

Ещё одна поправка к методике: замер идёт без `durationMs` (в выгрузке их нет), поэтому
балл длительности в нём всегда нейтральный. В приложении он будет работать и заметно
отсечёт часть ошибок — но и правильные совпадения для sped-up версий, у которых длительность
отличается от оригинала. Для треков с маркером версии допуск по длительности должен быть
отдельным и более широким.

## План

### Шаг 1. Нормализация названия (самый дешёвый, даёт самый большой прирост)

Разобрать `Title` из SoundCloud на `title` и `artists` до обращения к провайдерам. Отбрасывать
bracketed-сегменты `[...] (...)`, хештеги `#tag`, `prod. X`, `ft/feat/with X`, маркеры версий
(`slowed`, `sped up`, `reverb`, `bass boosted`, `remix`, `flip`, `mashup`, `rework`, `nightcore`,
`8d`, `bootleg`, `slow version`).

Из `A - B` строить матрицу кандидатов в обе стороны: `A` может быть названием, а `B`
исполнителем (`PIXELATED KISSES - JOJI`), или наоборот, продакшером и треком
(`Suicide Boys - Antartica`). Пробовать оба порядка, а не угадывать.

Отдельно добавить вариант «только название»: `GET /api/search?q=<clean title>` не требует
`artist_name` в отличие от `/api/get` (который на этом отвечает `400 missing field
artist_name`). По данным замера этот вариант находит оригинал для сторонних загрузок,
которые не находятся по паре «название + исполнитель» — см. «Находка замера».

Но ставить его в основной путь нельзя: на всех 18 непокрытых треках он даёт около двух
верных и шесть заведомо неверных результатов. Это последний рубеж с обязательной проверкой
длительности, а не первый запрос.

Реализация — чистая функция рядом с `parseLRC`, покрывается юнит-тестами в `main_test.go`
без сети.

### Шаг 2. Принимать `plainLyrics`

Расширить `lrclibLyricsResponse` полями `PlainLyrics`, `SyncedLyrics`, `Instrumental`,
`Duration`, `ArtistName`, `TrackName`. `Instrumental` — это однозначный ответ «текста нет»,
сейчас он молча игнорируется. `Duration` нужен для проверки кандидата.

Считать попадание и по plain-тексту. Это отдельный слой к шагу 3, поэтому в бенчмарке он и
измеряется отдельно.

### Шаг 3. Перейти на `/api/search` как основной путь

`/api/search` не требует точного совпадения и не требует ключа, возвращает до 20 кандидатов
вместе с текстом — то есть в большинстве случаев одного запроса достаточно, `/api/get` по id
нужен только для дозагрузки. Exact-`/api/get` оставить как быстрый путь для совпадения «в лоб»
и как источник таймингов.

**Обязательно:** повторы с backoff на `503` (шаг 8 диагноза), общий лимит параллелизма и
счётчик троттлинга. Лимит общий по IP, поэтому «добавь ещё один вариант запроса» —
это не только медленнее, это ещё и давление на единственный открытый источник. Матрица
вариантов из шага 1 должна ограничиваться по числу запросов на трек, а не перебираться
без конца.

### Шаг 4. Проверка кандидата (это про корректность, не про покрытие)

Каждый кандидат перед принятием должен проходить скоринг, иначе расширение поиска резко
усилит проблему №5 из диагноза. Эталонная реализация скоринга уже есть в
`scripts/lyrics-coverage.mjs` (`tokenOverlap`, `durationScore`, `scoreCandidate`) — её логику и
пороги нужно перенести в Go один в один, чтобы бенчмарк и приложение мерили одно и то же.

Политика приёма — из раздела «Находка замера»: название строго, длительность близко,
исполнитель не влияет на вердикт. Отдельно отвергать `instrumental` и кандидатов, чей
последний тайминг выходит за длительность трека.

Порог по названию — жёсткий. Лучше показать «лирики не найдены», чем подсунуть чужой трек.
Проверить границы можно прямо на замере: `I H3ART YOU → BOY FANTASY` должен проходить,
`Just Staring → John Lennon` — нет.

### Шаг 5. Тайминги для ненумерованного текста

Разложить `plainLyrics` по длительности трека: `startMs` пропорционально номеру строки, с
пропуском вступления. Тогда `isSynced` можно выставлять, и `LyricsSidebar` подсветит активную
строку. Для slowed-версий это даёт правдоподобную, хотя и не точную, синхронизацию — визуально
это уже воспринимается как «лирики работают».

Что делать с `isSynced` и `hasTimedLyrics` в `LyricsSidebar.tsx:101` — решить при
реализации: либо выставлять `isSynced` для синтетических таймингов, либо ввести отдельный флаг
в `TrackLyrics` (`models.ts:51`), чтобы UI не врол, что это реальная синхронизация.

### Шаг 6. Кэш

Кэш в `dataDir` рядом с `settings.json` (`main.go:372`), ключ — `trackId` плюс версия схемы
поиска. Значение — найденный `trackLyrics` плюс дата, чтобы протухание можно было контролировать.

Кэш решает три задачи сразу: сайдбар открывается мгновенно, лимиты Genius не тратятся на
повторы, а попадания видны локально без сети — то есть метрику покрытия можно улучшать вручную.

### Шаг 7. Описание SoundCloud как источник

`trackLyricsParams` (`main.go:211`) дополнить `Description`, `DurationMs` уже есть. Перед или
после провайдеров разбирать описание: убрать ссылки SoundCloud, найти блок строк, отсечь
служебные хвосты вида «prod.», треклист, ссылки на соцсети.

Для unreleased-треков это часто единственный источник. Проверить гипотезу нужно до
реализации — на датасете это единственный способ поднять длинный хвост, но текста в
описаниях может не оказаться, и тогда шаг не даст ничего. Это измерить, а не предполагать.

### Шаг 8. Пользовательские лирики

Сейчас в UI нет способа добавить текст вручную. Добавить в сайдбар режим правки: пользователь
вставляет текст, он сохраняется в кэш из шага 6 и отдаётся приложению как обычные лирики.

Дальше — опциональная отправка в LRCLib через `POST /api/put` (эндпоинт существует, требует
подписи). Это превращает личный список треков в общий вклад: пользователи закрывают ровно тот
длинный хвост, которого нет в базе. Отправку делать явно по нажатию, не молча.

### Шаг 9. Genius оставить как последний рубеж

Использовать только после отказа остальных источников, только с проверкой по шагу 4, с
уважением к лимитам и кэшем. Парсинг HTML остаётся слабым звеном — это осознанный компромисс,
а не решение.

## Чего не сделать

- Не подставлять непроверенный результат. Расширение поиска без скоринга даёт много текста и
  много чужого текста одновременно.
- Не отправлять в Genius запрос на каждый открытый трек — кэш и лимиты обязательны.
- Не собирать логи с идентификаторами треков на стороне Genius ради метрик.

## Длинный хвост

18 треков из 41 не находятся ни одной стратегией. Проверено точечными запросами, что это не
дефект запроса, а отсутствие записей: `Taida` в базе нет вообще, у `Girls Rituals` есть
`HRT` и `No Problems`, но нет `I Want Things to Be Beautiful`, у `Suicide Boys` есть серия
`SB-`, но нет `Antarctica`. Это unreleased-материал, который никто не публиковал текст —
`SAKEI (prod. Miler)` с 361 прослушиванием, `cachalot #2016`, `xerces - deftones`,
`юпи - никогда не умел`.

Такие треки не закрываются ни одним провайдером, сколько бы вариантов запроса ни
перебиралось. Единственные пути — ручной ввод (шаг 8) и описание трека (шаг 7).

Отсюда честная граница. Провайдеры дают 56% покрытия и 56% синхронизации на этой библиотеке.
Дальше — только пользовательский вклад; дойти до «большинства» без него нельзя. План считать
успешным по доле хитов и по вкладу в хвост, а не по 100%.

## Критерии готовности

- Бенчмарк на `scripts/lyrics-sample.txt` даёт 23/41 (56%) на стратегии `E_normalized`
  и 23/41 синхронных на `F_synthetic`, при `reliable: true` в JSON-отчёте.
- Ноль случаев, когда принятый текст не прошёл скоринг (регекс на выборке).
- Повторное открытие сайдбара не вызывает сеть — проверяется на включённом кэше.
- `GENIUS_API_KEY` перестаёт быть обязательным для показа лирики: текст находится и без него.
- `go test ./...` в `backend` зелёный, новые тесты на нормализацию и скоринг без сети.
